# Observing an interrupted turn from app-server clients

Cloud test against real `codex-cli 0.166.0`, using a private synthetic Codex home, a synthetic provider serving a deliberately unfinished response, two separate WebSocket clients connected to one local app-server, and a third client connected to a second local app-server using the same synthetic home. The controlling client started a thread and turn and called `turn/interrupt` for that exact turn. A second client resumed the same running thread through the same app-server before interruption. Both clients received a real `turn/completed` notification naming the same thread and turn with status `interrupted`. The third client's `thread/resume` against the separate server failed with `already has an active writer`; it received no completion notification during the subsequent 1.2 seconds. This establishes no general guarantee about every server version, reconnection, notification backfill, or real installations. These are real Codex processes, but provider, thread, and data are synthetic; neither model execution nor delivery was verified. The harness uses fixed Cloud fixture paths and an existing locally installed websocket package and Codex CLI. It is not a hosted-CI test.

A separate attempt to capture a real Stop hook in the same app-server did not produce a Stop hook in this fixture: only one synthetic provider response completed and the hook capture file was absent. It cannot establish a Stop payload or deduplication with this notification. Existing independent synthetic-provider CLI proof and the separate no-turn-ID counterexample remain relevant. The new Rust regression maps a synthetic notification into the existing coordinator-alert fingerprint and checks that Stop with the same stable turn ID and pending digest claims once, in both claim orders, including an uncertain first result. It also proves a Stop with no turn ID generates a different key. The mapping is test-only: this commit does not subscribe to `turn/completed`, notify a coordinator, or solve the no-ID case.

The active Wake receiver launches its own app-server. The observed active-writer rejection prevents assuming that it can subscribe to the real responsible thread through that separate server. A viable integration still needs a verifiable route to the responsible thread's actual app-server, lifecycle/disconnect recovery, and safe correlation with Stop payloads without an ID. Never suppress the pre-existing Stop notification merely because an ID-less hook might correspond to a live notification; do not resend an uncertain attempt.
