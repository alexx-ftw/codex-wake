# Active-alpha source compatibility: isolated counterexample

The coordinator reported a read-only measurement of the active receiver executable and installed plugin binary, both SHA-256 `0035ce01c51b7fa12a1d208f3a15450265e92c6df04a4648fb329fd5c760bdd8`. The coordinator also reported a historical local acceptance receipt linking that binary hash to source commit `0a1ba30162265efda9ffacf4f304602409873d11`, and a `runtime.json` source digest of `192e728ca2236f50adeec378b58f58103de6cb007ab82eda6ea7c23d40925080`. Applying that commit's `manager::source_digest` algorithm to its archived source in Cloud independently produced the same source digest. These are the reported measurements and source-level corroboration; this Cloud probe did not inspect or modify the deployed service.

For comparison, the publicly published `v0.2.0-alpha.1` archive passed its published SHA256SUMS, but its embedded binary SHA-256 was `1cecb0584bb8d6d066eac8864e72dce6eed0e7d7e0e2f8960741b9f268ce823a`, not the reported active binary hash. A version label alone is therefore insufficient to identify the active binary.

The Cloud tests used an executable rebuilt from `0a1ba30162265efda9ffacf4f304602409873d11` (SHA-256 `d57da01cdc87eee3e2231a6592282d6c4c3adc812489dbf7bf700ece42d7dde0`) and one built from `520109dbbf69332fafaa6cdccdee9e85b26c30d1` (SHA-256 `54482129be257b67c1ab4c5cc9de9498959968d4bc0e29808254393c233696bd`). The rebuilt old binary is **not byte-identical** to the reported active executable, so the test corroborates behavior of the recorded source; it does not execute the active binary.

## Missing required source field

In [required-source-receipt.json](required-source-receipt.json), the same new-version synthetic subscription required `details.required`, absent from the manually supplied Stop event. With the rebuilt 0a1 receiver process, the fake queue was called once and its message **did not** contain the missing-field warning. With the 520 receiver process, the fake queue was called once and its message **did** contain that warning. Both records became `queued` after fake acceptance; this is a difference in message content, not a claim that 520 blocks delivery. In both cases an unrelated synthetic subscription remained waiting and the receiver PID stayed unchanged. The [harness snapshot](required-source-harness.cjs) requires separately prepared local binaries and a WebSocket package.

This agrees with the source comparison: 0a1 dispatch selects the older subscription fields and does not inspect `required_source`; 520 dispatch reads it and adds the warning. The newer receiver also has dispatch/polling paths absent from the 0a1 receiver, including dependency notices, obligation and circular-wait dispatch, and delivery-evidence polling. The old dispatcher also does not use the newer `source_event_key` delivery path. These source differences are not themselves proof of a particular duplicate or lost message, but they rule out assuming full functional equivalence based on the earlier bfe5b59 probe.

## Limited schema migration probe

In [schema-receipt.json](schema-receipt.json), an old 0a1 CLI created two synthetic subscriptions and an old receiver process remained alive while a 520 hook initialized the same temporary database. The new schema added `required_source`; the unrelated subscription remained waiting with the same ID, both subscriptions remained present, and the old receiver made exactly one fake queue attempt for the test event. Fake acceptance ended `queued`; fake nonzero exit ended `needs_attention`, with no second attempt after repeating the hook. The [schema harness snapshot](schema-harness.cjs) requires separately prepared local inputs. This demonstrates only the particular additive migration and delivery scenarios in the fixture, not full bidirectional compatibility or preservation of every kind of subscription.

All database files, subscriptions and IDs in these fixtures were synthetic and isolated. The receiver executables were actual processes but were **not** launched by systemd. The control WebSocket and queue were simulated, and Stop was invoked manually rather than automatically by Codex. Initial fixture attempts failed because of a SQLite constructor argument and an incorrect expectation that 520 would block instead of warn; the retained receipts are from corrected fixtures. No actual message delivery, production schema migration, compatibility alias or activation was tested.

**Conclusion:** do not treat the active 0a1-era receiver as compatible with the full 520 behavior or install a compatibility alias on the strength of the earlier bfe5b59 receiver probe. A lossless runtime cutover or a deliberately limited, verified compatibility layer remains unresolved. The existing requirement to fence old hooks and launchers across all relevant hosts and process namespaces remains independent of this receiver incompatibility.
