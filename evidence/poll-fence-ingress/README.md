## Necessary conditions for a receiver handoff

A lossless cutover cannot be demonstrated for arbitrary webhook events from the current evidence: an unretained event can arrive during the gap and disappear. A feasible protocol requires an already-present, demonstrably durable upstream ingress capable of retaining every event before acknowledging it, preserving source identity, and handing events to the replacement with durable acceptance and explicit handling of ambiguous acknowledgements. Neither this capability nor such a proxy is established in the installed environment. In particular an HTTP 200 from the standalone webhook is not proof that a downstream Codex message was received.

Before any real activation, establish a gate preventing subsequent old hook and poller launches; drain and identify existing old processes, ingress requests and claims; preserve all state and subscriptions; resolve any uncertain in-flight delivery by inspection rather than automatic replay. Only after the gate and drain can a verified new dispatcher take ownership. A lock inode must not be removed/replaced while pollers may hold it. Keep ingress durable across the cutover and reconcile only sources with a documented retained history, exact identity, adequate pagination and authorization. Snapshot-only sources cannot recreate transitions that came and went. The old binary does not participate in the new polling fence, and old/new dispatch compatibility is not established. This is a conditional design, not an executable or validated production procedure.

The polling regression test in the code commit runs two OS processes with deliberately out-of-order synthetic responses; it checks that the old response is skipped before acceptance and the cursor remains at the newer response. The mechanism cannot make a snapshot source reveal unobserved transitions, and a crash after acceptance but before saving the poll state remains subject to existing claim and uncertainty semantics.
