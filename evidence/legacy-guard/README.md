# Legacy-key guard: isolated process evidence

This experiment builds on `e56479eede063990cbb8b06d67dcc7b43e967aff`. With a shared legacy fingerprint, the new implementation atomically inserts a legacy-key guard and claims the full-snapshot alert before sending. The guard has `needs_attention` storage state and reason `compatibility_guard_not_delivery`; it is not an attempted or verified delivery. The new status output reports only a guard count separately and excludes the guards from alert status/queue telemetry. An older executable still sees the guard as an existing legacy claim; its old status/telemetry can show the guard as `needs_attention`, but never as queued delivery. Guards have no automatic expiry.

[receipt.json](receipt.json) contains 12 isolated cases: old/new and new/old order and simultaneous invocation, with and without turn ID, each with a fake queue exit 0 or 1. After each case the harness invoked both hooks again. Every case made exactly one fake queue call. The process-level harness used the `bfe5b59946fab39ca93057f9324aefbf472761dd` Wake binary and the experimental new binary, temporary databases, explicit synthetic IDs and manually injected Stop payloads. The queue is fake; these are not automatic Codex hook executions or evidence of real delivery. The [harness snapshot](harness.cjs) requires separately prepared local paths and binaries.

[crash-receipt.json](crash-receipt.json) records a separate process test: the new Wake process was killed with SIGKILL after its fake queue began a blocking attempt. Reinvoking both the new and old executables produced no second attempt; the full claim remained `sending` and the guard remained a non-delivery record. The fake queue did not prove receipt, and this outcome preserves uncertainty. [crash-harness.cjs](crash-harness.cjs) is the local harness snapshot.

The unit tests additionally inject a failure between guard and full claim, drop an uncommitted transaction, simulate a restart after a committed sending claim, and race two connections against the same legacy key. Existing legacy claims remain diagnostic and are not resent. An uncertain full claim is not replayed.

**Limit:** this only serializes processes that computed the same legacy key. An old hook reads its first page before claiming; if that snapshot differs from the new transaction's snapshot, or the no-ID last message differs, the old process can compute a different legacy key and still send. The unit tests `stale_legacy_snapshot_can_still_claim_a_different_key` and `old_snapshot_before_pending_change_escapes_new_snapshot_guard` demonstrate this counterexample, the latter using actual fingerprints before and after a resolution. Thus a controlled version barrier is still required; this is not a proof of general mixed-version safety. If a guard's old key stays the same while items beyond the first page change, the new implementation can claim the different full digest while the old key remains reserved.

## Diagnostic size and retention

The guard reuses `coordinator_alerts` and adds no table. The existing legacy-collision diagnostics still retain the exact full pending snapshot in `coordinator_alert_collision_items`, plus metadata and two paginated tools. Removing historical values or retaining only a hash, IDs or the first page loses the ability to review a changed or resolved ninth item. Repeated identical collisions reuse their snapshot; distinct collisions and guards have no expiry and may grow without bound.

A smaller design could merge collision metadata into the existing alert row, keep a single paginated snapshot table and combine the two read interfaces, or move a canonical snapshot to a separately stored content-addressed blob. Each retains full historical values but needs careful migration and bounded reads. A strict storage cap requires an explicit retention/archival policy and necessarily removes or externalizes some historical evidence; it must not silently erase uncertainty or authorize a replay. Neither a schema consolidation nor retention policy is implemented here.
