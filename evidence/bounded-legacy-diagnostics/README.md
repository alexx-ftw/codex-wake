# Bounded legacy-collision diagnostics

This branch descends from `61625b742742ca0eb4c393bf5991d3b5b35bd391`. It does not contain or migrate the `e56479e` schema or its two collision tables; this alternative assumes that branch was not activated against the deployment database. The existing `coordinator_alerts` table stores at most one `needs_attention` diagnostic per legacy alert key. Its JSON message is capped at 16 KiB and holds only first and latest previews, each capped at 7 KiB and 16 obligations, with per-field limits, an explicit omitted count, a clipped-fields flag, the full snapshot digest, the pending count, the prior legacy alert ID and the corresponding new claim ID. Creation and the snapshot are inside the existing immediate transaction. A single paginated `inspect_legacy_alert_collisions` tool exposes that record, the prior legacy alert's persisted state and message, and the first and latest new-format claims if present. Stored messages are untrusted. A `sending` or `queued` state is not proof of receipt.

The hook does not send on a matching legacy claim and explicitly reports that delivery is not confirmed, alongside the diagnostic ID and the current digest and count. A repeated collision for the same legacy key updates the latest preview and observation time, preserves the first preview, and does not enqueue an alert, even if the old row was subsequently removed. The hook states that intermediate snapshots are not saved. A no-ID Stop can encounter the same legacy key after a turn barrier; it receives the same visible diagnostic rather than being silently suppressed.

## Limits

This is deliberately lossy for any observation with more than 16 items or fields larger than the per-field caps, and for intermediate snapshots between the first and latest under the same legacy key. The record flags preview omissions and clipping; the hook warns on every collision that historical details may not be recoverable. A digest can compare equality but cannot reconstruct omitted text or establish delivery. The operator can inspect current pending work with `list_obligations` and independently inspect the destination and any other retained evidence before deciding on manual action. If the omitted historical data is no longer available elsewhere, exact reconstruction is impossible. This branch does not claim complete historical recovery for those cases.

One diagnostic is retained per legacy key, without automatic expiry; after old producers are stopped, the maximum number of new diagnostic rows is bounded by the set of legacy keys. Existing alert storage itself remains persistent. No automatic pruning or acknowledgement is added. A finite storage limit and indefinite exact recovery of arbitrary historical snapshots cannot both be guaranteed without an explicit archival/retention policy or external storage.

## Activation boundary

Publishing or testing this branch in Cloud does not activate it or alter runtime data. Enabling it in a deployment requires the coordinator's barrier: prevent new old-version launches, drain all old hooks and turn processes on every relevant host and process namespace, verify no old launcher can run, and only then switch runtime binaries while preserving subscriptions. A version barrier does not solve future no-ID collisions; this design records matching collisions but cannot correlate different legacy fingerprints. The mixed-version counterexample remains documented at `cb3710be71815c9c75705826e464806f1632d5da`. No automatic send is authorized as a recovery action.
