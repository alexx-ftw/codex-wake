# Read-only turn state from another app-server

Cloud proof using real Codex CLI 0.166.0 with an isolated synthetic home and provider, no real conversations or delivery. One app-server owns a thread with an actively streaming turn. Another independent app-server shares only that synthetic home. Before sending `turn/interrupt`, the owner reports that exact turn as `inProgress` through both `thread/read` and `thread/turns/list`; the independent server reports the same turn ID as `interrupted` from both methods, with thread status `notLoaded`. Attempting `thread/resume` on the second server reports an active writer. After interrupting, the owner emits a real `turn/completed` with that ID and `interrupted`; the independent server still reports the same `interrupted` status, including after reconnection. Thus the independent read is not evidence that interruption happened and cannot reliably detect this event by transition.

A client subscribed to the owner app-server was intentionally disconnected before interruption. On reconnection it did not receive a replay of `turn/completed` in the observation window, but the same owner server's `thread/turns/list` did return the interrupted turn. A still-connected client received the notification. This single run does not prove durable replay, all disconnect/crash races, behavior after the owner unloads the thread or behavior of another Codex version. The handler never executed Stop and did not send coordinator alerts. The harness has Cloud-specific fixture paths and is not part of hosted CI; its assertions validate the recorded observations. The associated code starts from f61cf7ab3688c170dd03308ef99ca971784ddd91.

Wake's existing metadata poll deliberately does not treat `interrupted` as a completion. The candidate change adds the informational reason `interrupted_status_unverified` to its existing status for an interrupted baseline or observation, and clears it on another successful status. It does not create a subscription, send a notification, infer actual interruption, change Stop delivery or resolve the absent-turn-ID correlation. Its unit test uses mocked RPC and is not this real Codex integration test. A viable notification still needs a verified connection to the actual owning app-server, a reconnect strategy that distinguishes loaded authoritative state from reconstructed state, and a safe correlation with Stop without a stable ID; the candidate alone does not implement that feature.
