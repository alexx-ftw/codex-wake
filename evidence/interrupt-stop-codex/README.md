# Experimental same-turn Stop and Interrupt observation

On 2026-11-07, a Cloud fixture ran Codex CLI 0.166.0 with the experimental Wake implementation in parent commit `bd564e1975b806617a4201142836ad6487009ccb`. The tested local debug Wake binary had SHA-256 `60afa0f23f91a254a3bdc0b627e5122ec01244295de643f54aebb21c2ccfa047`. The receipt is [receipt.json](receipt.json); its UUIDs refer only to this fixture.

Codex received a deterministic assistant response from a synthetic local HTTP provider. The fixture had inserted one pending obligation and an explicit coordinator directly into its isolated SQLite database. Codex automatically invoked Stop, which returned `decision: block`. When Codex requested the next model response, the harness sent SIGINT. Codex then automatically invoked Interrupt. The two captured inputs contained identical `session_id` and `turn_id`. The experimental Wake executable ran for both hooks; exactly one coordinator-alert row was queued and the fake queue executable was called once. The pending obligation remained unresolved. The Codex exit code 1 is expected for this interrupted run; the harness exited 0 after checking its assertions.

Both hooks were invoked by the actual Codex runtime. A Node wrapper recorded selected fields and delegated to the experimental Wake executable with explicit isolated database and queue paths. The provider and queue were simulated, plugin hook trust was bypassed in the fixture, no systemd service was used, and queue acceptance does not establish delivery or receipt. The setup initialized the database by a separate manual hook invocation; that invocation is not counted as either observed runtime event. [harness.cjs](harness.cjs) is the executed harness snapshot and depends on the separately prepared fixture paths, installed Codex and built Wake binary; it is not a standalone reproduction script.

This observation covers Stop followed by Interrupt with the same ID. It does not establish behavior for every version or host, a missing Stop ID, the opposite order, concurrent invocations, process failure, or actual notification delivery. The implementation remains experimental: without a stable Stop ID the two signals cannot safely be correlated, and a duplicate alert is possible. Do not integrate it as a complete no-duplicate solution on the basis of this receipt.
