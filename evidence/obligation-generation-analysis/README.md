# Obligation-generation deduplication: contract analysis

Base: `bfe5b59946fab39ca93057f9324aefbf472761dd`. This branch contains evidence tests and this analysis, not a production implementation. The test fixtures run the real base Wake executable with manually supplied hook payloads, temporary databases and fake queue commands. They do not invoke Codex's hook runtime or contact an actual coordinator.

## Counterexample to preserving existing Stop semantics

A single pending obligation `A` exists. On Stop for turn `T1`, the current implementation claims and attempts one alert. On a later Stop for `T2`, `A` still has the same identity and state; current Wake claims another alert, including the new Stop context. `evidence_distinct_turns_notify_for_unchanged_pending_obligation` checks this with both queue acceptance and a nonzero queue exit, while repeated `T1` is deduplicated. A key `(coordinator, obligation A, version)` sends at most once and therefore suppresses the second Stop, even if the responsible agent resumed and stopped again. It also suppresses the second event when `T1` has an uncertain send; that avoids resending the old notice, but gives up reporting the new stop. This is a change from the documented per-Stop contract, not evidence that the old delivery occurred or that the second turn was reported.

For a Stop with no ID, `evidence_unidentified_stops_with_new_last_message_are_distinct` checks that the existing contract distinguishes a new last message. A key only by the unchanged obligation does not. Conversely, the separately recorded [no-ID counterexample](https://github.com/alexx-ftw/codex-wake/tree/bb46387c90fd5f266568997c596c2001d2050468/evidence/interrupt-stop-codex/no-id) shows why independently keying an Interrupt and a no-ID Stop can produce two uncertain sends. A no-ID Stop with unchanged work is observationally ambiguous: it can be another hook for the same turn or a genuinely later stop. Obligation version alone does not distinguish those histories. One cannot both preserve the existing per-stop notifications and suppress all such duplicates from these inputs alone.

## Change detection and atomicity

`evidence_ninth_pending_obligation_is_outside_current_fingerprint_page` shows a separate base limitation: only the first eight pending obligations enter the current fingerprint. With the same turn ID, adding a ninth obligation leaves that fingerprint unchanged and no new alert is sent. A generation for the full pending set could detect this change, but must not merely hash the displayed first page. A new notice must describe the changed/new item or give a reliable cursor; repeating an earlier uncertain message is not proof of delivery.

A production design would need an atomic transaction for the pending snapshot, generation and claim, coordinated with every relevant mutation: registration, resolution, transfer/recipient changes, and coordinator changes. A monotonically increasing version avoids an A→B→A state returning to the same hash. A stable per-obligation generation and a durable claim linked to each item can separate a newly added item from prior items whose sends are uncertain; including old items as background must not be mistaken for verified delivery. Sending must happen after the transaction, with claims retained in sending/uncertain or needs_attention states and no blind replay. Resolution or transfer can race the subsequent send, so the message must report the snapshot and avoid claiming current state or successful receipt. A pending obligation transferred away and later back, or assigned to a new coordinator, needs explicitly defined coverage and versioning.

Migration is nontrivial: existing coordinator alert IDs are hashes of prior fingerprints and the full previously covered obligation set is not recoverable from the ID. Starting new generation claims without a migration barrier can resend an uncertain historical notice. Reusing a legacy hash only when the old current snapshot matches does not solve changed snapshots. Generation coverage also cannot establish receipt, infer work not registered in Wake, or detect hard process death without a reliable hook/event.

Accordingly, do not integrate an obligation-only key as a drop-in fix. An implementation is possible only after the desired semantics for a later stop with unchanged obligations are settled or a reliable event correlation becomes available. The existing `bfe5b59` implementation is unchanged by this evidence branch.
