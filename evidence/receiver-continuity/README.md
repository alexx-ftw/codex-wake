# Isolated receiver continuity probe

> **Scope correction:** The fixture below compares `bfe5b59` to `520109db`; it does not represent the reported active receiver. The [0a1ba30 source compatibility probe](../alpha-receiver-compatibility/README.md) found a real missing-warning behavior difference, so this earlier result must not be used to approve coexistence of the active alpha receiver and the new runtime.


On 2026-11-07, a Cloud fixture ran a real Wake receiver **process** built from `bfe5b59946fab39ca93057f9324aefbf472761dd` (binary SHA-256 `58e83f44bc717ca191635404366f54691d6ec815870243620b2b7591455c5a02`) while invoking the `520109dbbf69332fafaa6cdccdee9e85b26c30d1` Wake hook executable (binary SHA-256 `54482129be257b67c1ab4c5cc9de9498959968d4bc0e29808254393c233696bd`) with manually supplied Stop payloads. [receipt.json](receipt.json) contains the observed results. [harness.cjs](harness.cjs) is the executed fixture snapshot and depends on separately prepared binaries and a local WebSocket package; it is not standalone.

The old CLI registered two synthetic subscriptions in a private temporary SQLite database: a thread/turn_completed subscription and an unrelated artifact subscription. The fixture inserted a synthetic pending obligation directly. It started the old receiver and used the new executable to process the same Stop twice. A separate fake Codex queue command recorded the caller PID. In both synthetic acceptance and synthetic nonzero-exit cases, the same old receiver PID remained alive, it was the parent of exactly one fake queue attempt, the unrelated subscription remained waiting with the same ID, both subscriptions remained present, and the repeated Stop produced no second queue attempt. The target subscription ended `queued` on fake acceptance and `needs_attention` on the synthetic error. Queue acceptance does not prove receipt; a nonzero exit does not prove non-delivery.

This probe did **not** activate an update, exercise `systemd --user`, replace a plugin, install a compatibility alias, use a real app-server, GitHub, webhook ingress or real subscriptions. The controller WebSocket, queue command, source event and obligation were simulated; the receiver and hook executables were real processes. The Stop hook was invoked manually, not automatically by Codex. The earlier fixture attempts included a fake queue returning an unexpected failure and an SQLite lock; these were test-harness failures, not evidence of production behavior. The retained receipt is from the corrected fixture, which used a busy timeout and cleaned up its own processes.

# Upgrade boundary and unresolved work

The repository comparison between the two exact commits found no differences in `src/manager.rs`, `src/bridge.rs`, `src/subscriptions.rs`, `src/polling.rs`, `src/observers.rs`, `src/native_poll.rs`, `src/execution.rs`, `src/rules.rs`, `src/circular_waits.rs`, or `hooks.json.tmpl`. Changes to `src/main.rs` and `src/obligations.rs` still affect the full source identity. Applying the source-digest algorithm from `manager.rs` to the archived trees produced `6180d13038bfe38111a5a0c2fc10f4165ec48e21b170b917efc5ad603b53297a` for `bfe5b59` and `d915c28dfb99de6d185e93a8d1a4a8409702fdd0ad9add74d6c06fd9453d8aec` for `520109db`. These are local build-input calculations, not observations of any deployed runtime, and unchanged source files are not by themselves proof of safe deployment.

The existing `compatible_sources` stamp check accepts an explicit source digest only after the stored binary checksum and hook template match; its unit test covers the checks. That mechanism does not establish semantic compatibility, stop stale hooks, install or verify an alias automatically, or prove a deployed process cannot be replaced or restarted. The repository's `service.lock` guards service installation/removal operations, not all hook launches or already-running hook processes. The bootstrap `flock` protects release-cache installation, not the lifecycle of hooks. Therefore neither lock alone is an upgrade barrier.

A possible narrower deployment path is to leave a verified old receiver and its subscriptions active while a reviewed compatible client/hook version is introduced **only after** a controller-enforced gate prevents old hook launches, all old in-flight hooks have drained across all relevant hosts and process namespaces, and no alternate old launcher can start. Independently verify the old receiver's process identity, executable, unit, source and binary stamp, exact database and hook configuration, plus schema/dispatch compatibility for the exact versions, before considering any compatibility declaration. Keep the gate until the new launchers and clients are in use. An old hook that took a different pending snapshot can still send a separate alert, so a process snapshot or same-key sentinel is not sufficient. Do not terminate or recreate subscriptions, and do not automatically replay uncertain deliveries.

This document is evidence for investigation, **not** a verified zero-downtime updater or an instruction to modify a running service. The current maintenance procedure stops the receiver, during which source events may be missed; source replay is not guaranteed. The Cloud probe did not establish a real gate, compatibility alias or deployment. The coordinator reported a live receiver and nine additional cached-plugin processes, but that observation is a point-in-time snapshot and does not prove that all old launchers are fenced.

The optional automatic goal reactivation remains unimplemented: `thread/goal/set` has no conditional compare-and-set, and the previously reported [isolated goal test](https://github.com/alexx-ftw/codex-wake/actions/runs/42327849485) showed that an automatic activation can overwrite a concurrent pause. An explicit `resume_goal` exists, but it is not evidence of safe automatic reactivation. The Interrupt work and missing-turn-ID ambiguity remain open; this probe does not demonstrate an automatic coordinator notice on interruption.
