# Mixed-version coordinator alert race

On 2026-11-07 in Cloud, an isolated harness invoked the Wake executable built from `e56479eede063990cbb8b06d67dcc7b43e967aff`, followed by the Wake executable built from `bfe5b59946fab39ca93057f9324aefbf472761dd`. Both received the same manually injected Stop payload and shared a temporary SQLite database containing one synthetic pending obligation and coordinator. The local queue executable was a fake that logged each invocation. [receipt.json](receipt.json) records two fake queue calls, two different alert IDs, two queued records, and two Stop blocks. The [harness snapshot](harness.cjs) depends on separately prepared local binaries and paths; it is not a standalone reproduction. This does not exercise the real Codex hook runtime or actual message delivery.

The old executable derives and claims only the legacy key. If the new executable claims the full-snapshot key first, the old executable cannot see that as its own legacy claim and can send again. The new executable's legacy collision detection protects the opposite order, but cannot change the already-running old executable. **Mixed-version execution is not safe from duplicate sends.**

An upgrade barrier must prevent any old executable or launcher from beginning or continuing a hook that can send while the new version is enabled. On every host, container and relevant process namespace that can access the shared Wake database or launch hooks, first gate new eligible turns/hook launches under the controller, allow existing controller-owned turns and hooks to finish, and wait for every old hook process and any launcher capable of starting its old binary to exit. Verify this through the authoritative controller/supervisor state together with process-tree and executable inspection in each namespace, including old cached copies and deleted/replaced executables. Ensure no external client, timer, detached process, alternate installation or host can start the old implementation. Keep the gate active while switching all installations and confirming the binary/version used by subsequent launches. Preserve subscriptions and queue records throughout. A one-time process listing, stopping only the receiver, or inspecting only one host does not prove the barrier. If the deployment cannot establish all of these facts, mixed-version safety remains unproven.

A barrier also does not resolve the ambiguity of later Stop hooks lacking a turn ID. The implementation records a durable collision and does not automatically send when the old fingerprint matches; differing old fingerprints cannot be reliably correlated and require manual verification.

## Collision snapshot use and retention

The collision record identifies the historical alert, the corresponding full-fingerprint claim, their persisted states/messages when available, observation count and the captured message. `list_coordinator_alert_collisions` paginates these diagnostics; `list_coordinator_alert_collision_items` paginates the exact saved obligation snapshot, including values that may since have changed or been resolved. They provide evidence for manual investigation, not proof of receipt and not a replay mechanism. Repeated observations of the same fingerprint reuse the snapshot; the count includes repeated hooks and does not imply distinct turns.

The current code provides no expiry, acknowledgement, pruning or separate retention limit for these collision records or snapshots. They persist in the Wake SQLite database until that database is removed; each distinct collision can retain a full pending snapshot, so total storage can grow with both collision count and pending-set size. Treat stored descriptions and messages as untrusted and potentially sensitive. Cleanup is subject to the existing owned-database uninstall checks.

Keeping only the first page, a count, IDs or a hash would not preserve the exact historical descriptions and fields after an obligation changes or resolves, and the old hash cannot reveal which item was previously communicated. A different representation could retain equivalent evidence, such as a canonical stored snapshot with paginated decoding or content-addressed deduplication, but it still needs durable per-obligation historical values, atomic capture, bounded reads, migration and an explicit retention policy. Such a redesign may reduce duplication or table count; it does not solve mixed-version delivery or prove receipt. No retention or pruning policy is implemented by this evidence branch.
