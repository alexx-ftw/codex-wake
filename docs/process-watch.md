# Process output watch

`codex-wake [--db PATH] watch-process --subscription-id ID --regex PATTERN --timeout-seconds N -- PROGRAM ARGS...` starts a command for a waiting `job/completed` subscription. MCP starts the watcher in a dedicated transient systemd user service; closing the MCP connection or restarting `codex-wake.service` does not stop it. Process watching requires systemd 254 or newer, checked from `systemd-run --help` before launch. The service keeps the caller's working directory and environment, and passes the database as an absolute path. These values must be representable as UTF-8 for systemd. Use `process-watch-status` and its diagnostic log to inspect it.

Environment values travel through a mode-0600 file in the private `process-watch/` directory, not `systemd-run` arguments. A directory lock covers file creation through launch resolution, so cleanup and external-database uninstall cannot race a live launcher. The file is removed after `systemd-run --service-type=exec` confirms the command was executed. If launch times out, the code waits for the transient unit to become active or terminal. A manager query error or absent unit does not resolve the start: systemd's `StartTransientUnit()` returns after enqueueing a job, and a timed-out client may not receive that reply. The private file therefore remains until the manager exposes the unit as active or terminal; absence has no time-based expiry. If the manager never exposes it, the file and external database remain for manual investigation and cleanup. External-database uninstall refuses to delete the database while any environment file remains unresolved. Each transient path property is passed using its own systemd encoding; literal `%` paths are covered by an isolated user-manager test.

Generic expiry (`expires_in_secs` or `expires_at_ms`) is rejected: the monitor owns the deadline and persists selection before publication. SQLite `BUSY`/`LOCKED` retries preserve that selection and prevent expiry while publication waits.

stdout and stderr go to private files beside the database, under `process-watch/`; output is not copied to MCP. Before selection, logs are unbounded and can fill the filesystem. Matching runs independently on each stream, keeps a rolling 1 MiB window, and checks it together with each new 8192-byte block and up to four lookahead bytes. A candidate touching an artificial window edge is deferred while bytes remain beyond the lookahead. End-of-stream anchors such as `READY$` are not treated as final while the child is alive, even if the file is temporarily quiet at that point. After the direct child exit is observed, the watcher captures current file lengths and evaluates anchors against that snapshot; descendants holding the output descriptors may still append later, so this is not a claim that every process in the group has reached EOF. An empty stream is evaluated only after the child exit snapshot, so `^$` can match an empty captured stream without matching the temporary empty prefix of a silent live child. This preserves matches at window rollover, but patterns requiring more than about 1 MiB plus one block can miss; arbitrary unbounded context is unsupported.

Each pass consumes at most 8192 bytes per stream, checks for a match, then checks the deadline. This prevents continuous stdout from starving stderr or timeout. At timeout, unread bytes in the captured lengths make the result `observation_ambiguous` (`match` or `timeout`). On observed exit, both streams are drained to captured lengths in bounded chunks. If exit is first observed at or after the deadline, the result is ambiguous between `process_exit` and `timeout` even when the captured output is fully drained; unread bytes also add `match` as a possibility. A match observed at or after the deadline is ambiguous and includes `match` and `timeout`; `process_exit` is included when exit was also observed. If both streams match in one pass, stdout wins. Bounded child waits let early exit finish promptly.

After selection is committed, the watcher saves each stream's last 1 MiB to `<active-path>.retained`. Match context (up to 1 MiB plus boundary lookahead) is also saved in SQLite and `<stdout-path>.match` before truncation. Active files are truncated in place, so child descriptors keep writing. A reaper repeats this every 250 ms while the process group lives; it does not signal the child. Retained tails can omit concurrent writes between snapshot and truncation.

Retention is best-effort, not a strict quota: bursts, delays, errors, or descendants leaving the process group can add growth; preselection output is unbounded. Atomic replacement temporarily needs old and new retained files. At 1 MiB/s, 250 ms is about 0.25 MiB per stream, an estimate rather than a limit. Retained files and records remain after completion until an explicit policy removes them.

Delivery (`state`) and retention (`retention_state`) are separate. Reaper completion cannot publish an event. `published` plus `complete` is terminal for automatic recovery. Legacy `retention_error` records migrate to retryable `error` and enter the scheduler's candidate list. The full scheduler still refuses takeover when the saved supervisor identity has no verifiable PID namespace; it marks the record `needs_attention` and stops automatic retries. This legacy case needs identity verification or repair before manual recovery; automatic legacy recovery is not guaranteed. A final `failed` state also stops automatic retries; `recover-process-watches` retries after repair. In particular, if output-file device/inode identity is absent or no longer matches, retention cannot safely truncate or replace the file; restore the identity or inspect and repair the record before retrying. `needs_attention` remains recoverable while the child lives or retention is unfinished, except when identity validation has marked retention `failed`. Canceling the subscription does not signal or stop the child. If cancellation wins before publication, the selection stays durable, delivery moves to `needs_attention`, and output retention continues; the event is not delivered and the record needs manual inspection.

External database cleanup removes current diagnostic logs whose filename includes the database path fingerprint. Legacy `<subscription-id-hash>.monitor.log` files lack that database identity and may be shared by sibling databases, so cleanup preserves them instead of risking deletion of another database's log. Such an orphan may need manual removal after its owner is verified.

The receiver checks stale supervisors every second in a background thread independent of MCP clients; startup and SQLite retries do not block MCP initialization. If the receiver is down, recovery waits for restart or manual `recover-process-watches`. A watcher and its child share a dedicated transient service cgroup, separate from `codex-wake.service`. `KillMode=process` leaves the child running if the watcher fails; recovery uses a separate transient unit, and the receiver retries a failed takeover on its next scan. Stopping the whole user manager still stops both. Reaper and uninstall share the database-directory lock, and the reaper verifies the database device/inode before each retention pass. Crashes or scheduling gaps can add output before truncation; committed match context remains in SQLite.

The default `job/completed` message includes the reason and says a matched or timed-out child may still run. Ambiguous recovery lists possible events; event source is stored even without a custom template. `process-watch-status --subscription-id ID` reports identities, selection, delivery/retention states, paths, and diagnostics. Recovery reports scheduled PIDs, not confirmed resumptions.

Recovery resumes scanning when selection is absent, otherwise retention. It snapshots log lengths and scans in bounded chunks. Files cannot order match and exit during supervisor downtime, so recovery reports `recovery_ambiguous`; unread bytes at the deadline remain a possible match, while an empty scanned snapshot does not. Identity includes Linux boot ID, PID namespace, PID, and start time. Records without a verifiable PID namespace need attention; a crash before durable child identity is recorded is diagnosed and not relaunched. This starts a new local command; it does not attach to an existing `exec_command` or Codex app-server process.
