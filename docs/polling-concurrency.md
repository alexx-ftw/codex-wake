# Polling commit and cleanup limits

Each GitHub endpoint has a generation. A poll fetches outside the lock, then acquires an exclusive advisory lock on the canonical database's parent directory and compares the generation before accepting events and saving state. A successful save increments the generation in the same SQLite transaction as the cursor and cached pages. A response fetched against a different generation is skipped before acceptance; stale fetch errors also cannot overwrite a newer successful poll. A two-process test supplies deliberately out-of-order responses. The directory is the lock inode: no `.poll.lock` sidecar is created or removed, and different databases in the same directory serialize their short commit sections. Database hard links are rejected. Old executables do not use this lock or generation and must be excluded by a separate verified barrier.

Acceptance and the cursor transaction are separate. A failed cursor save can therefore leave an already accepted item with the old cursor. The tests inject failure during the generation update after acceptance, dispatch once through a synthetic failing Codex executable, then repeat acceptance and dispatch: both a workflow wait and a Git-ref subscription remain `needs_attention`, with exactly one simulated invocation. This establishes those paths and injected failure, not every rule, crash timing, actual delivery, or a general exactly-once guarantee. The workflow bridge returns `recorded` even on duplicates, so the polling accepted counter can count a duplicate despite there being no new ready row; it is not delivery evidence.

External-database cleanup takes the same directory lock nonblocking and refuses deletion while a poll commit holds it; cleanup of the managed state tree takes it after stopping registered clients and holds it through deletion. Pollers waiting on the old directory check that the database inode is unchanged after acquiring the lock. Cleanup still relies on the existing uninstall barrier against new launches and on stopping clients: replacing or recreating the entire database between opening it and acquiring its directory lock is outside this guarantee. A separate process test covers an active lock blocking external cleanup, followed by successful deletion after release. Since this version never creates a sidecar, that test checks no sidecar remains; it does not migrate or remove an orphan from an older unintegrated experimental build.
